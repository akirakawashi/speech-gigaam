# Архитектура speech-gigaam

## Части

| Часть | Где работает | Что делает |
|---|---|---|
| Triton | видеокарта, образ NVIDIA | держит энкодер GigaAM (движок TensorRT, fp16) и считает его по запросам |
| HTTP-процесс службы | процессор | принимает файл, ограничивает очередь, раздаёт файлы обработчикам, отвечает |
| Обработчики (N процессов) | процессор | декодируют звук, ищут речь, считают признаки, вызывают энкодер, декодируют слова |

Видеокарта нужна только Triton. В образе службы PyTorch без CUDA.

## Путь одного запроса

1. `POST /v1/transcriptions` с файлом в теле. HTTP-процесс читает тело с пределом
   размера и проверяет очередь: в работе и в ожидании не больше
   `GIGAAM_WORKERS + GIGAAM_QUEUE_LIMIT` запросов, иначе сразу 503.
2. Свободный обработчик получает байты файла по каналу между процессами:
   - PyAV декодирует звук в моно 16 кГц, как `faster_whisper.decode_audio` на стенде;
     для стерео копит громкость каналов блоками по 10 мс;
   - Silero VAD ищет фрагменты речи порциями по 100 мс (параметры как на стенде);
   - для каждого фрагмента — лог-мел признаки с окном и фильтрами из весов модели,
     энкодер в Triton по gRPC, жадный декодер RNN-T на ONNX Runtime;
   - из токенов собираются слова и текст реплики, из фрагментов — паузы.
3. Ответ: реплики с таймкодами, словами и громкостью каналов, паузы, сведения о
   звуке и модели. Форма полей движка, модели и реплик — как в контракте приёма
   распознавания бэкенда ([API](api.md)).

Слои кода:

```
domain          реплика, слово, пауза; сборка слов и текста; паузы между речью
application     сценарий одной записи, порты, ошибки с кодами, ответ API
infrastructure  PyAV, Silero, признаки, Triton, декодер, папка модели, пул процессов
presentation    FastAPI: /v1/transcriptions, /ready, /health, /v1/model
di              сборка HTTP-процесса и движка внутри обработчика
setting         настройки GIGAAM_*
```

## Процессы и сбои

- Обработчики — отдельные процессы (`multiprocessing`, метод `spawn`): поиск речи
  и декодер — циклы на Python, и потоки одного процесса мешали бы друг другу.
  Каждый процесс при старте один раз загружает модели, проверяет модель в Triton и
  прогоняет пробный фрагмент. Служба считается готовой, когда готовы все.
- Обработчик берёт одну запись за раз. Число потоков математических библиотек в
  нём — `GIGAAM_THREADS_PER_WORKER`.
- Обработчик упал во время записи → запрос получает `worker_failed` (500), на его
  место запускается новый. Не уложился в `GIGAAM_REQUEST_TIMEOUT_S` → процесс
  убивается и заменяется, запрос получает `timeout` (504). Новый процесс не
  запустился → попытки идут в фоне с растущей паузой, остальные продолжают работу.
- Запрос отменён вызывающим посреди записи → обработчик дописывает её и только
  потом берёт следующую: место в очереди освобождается по факту.
- Служба ничего не хранит. Повторная отправка того же файла даёт тот же результат.

## Почему так, а не иначе

- **Не «просто контейнер, как Whisper».** У GigaAM нет готового сервера с HTTP API:
  авторы выпускают Python-библиотеку. Готовый сторонний образ
  (`bampodev/ru-sst-tts-docker`) не проверен и работает на PyTorch.
- **Не PyTorch целиком.** На ПК 100 записей: TensorRT — 64 с, PyTorch — 662 с,
  Whisper — 885 с. Выигрыш от перехода даёт именно TensorRT.
- **Не официальная сборка GigaAM под Triton** (`triton_scripts` в репозитории
  GigaAM). Она принимает уже нарезанные фрагменты и не ищет речь в длинных
  звонках, отдаёт только текст без таймкодов и создаёт признаки заново, без окна и
  фильтров из весов модели — на стенде это меняло текст примерно в четверти
  фрагментов.
- **Код со стенда без изменений логики.** Путь проверен на 3 878 записях без ошибок;
  совпадение со стендом проверяется автоматически ([разработка](development.md)).
- **Файл в теле запроса, а не путь на общем диске.** Служба ни от кого не зависит,
  записи небольшие (3 минуты — около 800 КБ), передача внутри машины ничего не стоит.

## Чего нет в первой версии

- Голоса собеседников (CAM++) и эмоции (GigaAM-Emo) — полный режим стенда.
- Роли «оператор / клиент». Служба отдаёт громкость каждого канала по реплике;
  какой канал чей, знает вызывающий по источнику звонка.
- Подготовка модели внутри проекта: пока папка модели берётся у стенда ([модель](model.md)).
- Метрики Prometheus.
